# 安全拖放设计

> 状态：首期外部拖入已接入 `desktop_drop`、`DragDropController` 和现有导入链路，尚未完成三平台桌面验收。跨应用拖出仍保持禁止；代码接入和自动化证据不等于平台功能完成。

## 1. 目标

在目录浏览器中提供明确且可控的桌面拖放：

- 外部文件或目录拖入已解锁的加密目录，等价于用户点击“导入”。
- 默认不允许从加密目录拖出到系统文件管理器，避免把解密内容意外暴露到普通磁盘。
- 用户可在设置中显式开启“允许拖出解密副本”；每次拖出仍需确认明文暴露风险和目标冲突，不把该开关当作静默导出授权。

## 2. 边界与非目标

- 只接受本机普通路径，拒绝 URL、文本、HTML、虚拟文件、剪贴板承诺文件和未能解析为绝对路径的系统对象。
- 拖入不能绕过已有的目录导入、文件导入、名称冲突、进度、取消或 unfinished 状态处理。
- 不支持将加密条目拖到另一个已解锁 root 作为“移动”；该场景应使用现有应用内复制/剪切流程。跨 root 目录移动已具备 copy-then-delete 与部分完成保护，但不因而扩大首期外部拖放的范围。
- 不支持把 root 配置、内部草稿、unfinished 标记或应用私有缓存作为拖入/拖出对象。
- 首版不实现 Linux/Windows/macOS 之间不同文件管理器的虚拟文件协议，也不提供文件管理器内联缩略图。

## 3. 方向与交互

### 外部到加密目录

1. 拖放目标必须是已解锁 root 内的当前目录或一个已解锁子目录。
2. 进入目标时只显示“导入到此加密目录”，不显示来源绝对路径以外的额外敏感信息。
3. 放下后先生成导入请求，再复用现有冲突确认、Transfer 进度和取消界面。
4. 来源与目标同名时必须沿用“取消、保留两者、替换”策略；目录合并必须单独确认。
5. 用户取消、路径失效或权限不足时不创建目标条目；已开始的 Transfer 由现有 unfinished 规则感知，不显示伪进度。

### 加密目录到外部

1. 设置默认关闭，文案为“允许拖出解密副本”。
2. 开启后，拖起时先显示一次确认：目标是普通文件系统，副本将以明文形式存在；取消不创建临时明文文件。
3. 目标路径必须由系统拖放协议返回的实际绝对目录确认。若平台无法可靠提供目标目录，首版拒绝拖出，改为现有“导出”流程。
4. 导出继续走 Transfer，目标存在时沿用导出冲突对话框；拖出成功只代表生成副本，永不删除加密目录内的源条目。

## 4. 架构

```text
平台拖放适配层
  -> DragDropController（校验方向、路径、设置和确认）
  -> HomePage 导入/导出协调器
  -> DirectoryService / Transfer V3
  -> FFI / sec_fs
```

- 平台适配层只把事件转换为绝对路径列表与目标目录，不拥有 root ID、密码、文档 token 或文件内容。
- `DragDropController` 是唯一的策略入口：拒绝不支持载荷、检查 root 会话、显示确认，并生成既有导入/导出请求。
- Transfer 不因拖放创建第二套进度、锁或恢复格式；同一操作只能有一个进度面板和一个 unfinished 状态。
- 不记录拖放来源、目标或临时明文路径到偏好设置、日志或 root 内标记。错误报告仅保留脱敏后的操作阶段。

### 首期实现接口

首期只实现输入方向，分为三层，禁止 `DropTarget` 直接调用 `DirectoryService`：

1. `DesktopDropAdapter`：仅把 `desktop_drop` 的 `DropItem` 转为候选路径。`fromPromise`、内存 bytes、空路径和非绝对路径在此层拒绝。
2. `DragDropController`：对候选路径去重并检查路径当前存在、类型为普通文件或目录、没有落在当前加密 root 内；输出按原顺序的文件/目录导入请求。它不接触 root ID、密码或 Transfer。
3. `HomePage`：确认当前 root 会话仍有效，按请求顺序复用现有文件/目录导入冲突、进度、取消与 unfinished 处理。任一项取消或失败不隐式处理后续项，也不创建第二套 Transfer 状态。

`HomeShell` 的目录浏览区域只在当前 root 已验证且不在 loading 状态时显示拖入高亮。锁定 root、侧边栏、应用栏和设置页不能成为 drop target。首期不支持投递到未展开目录节点，统一导入当前路径。

## 5. 平台方案与前置调研

平台验收前必须确认所选 Flutter 桌面拖放方案在 Linux、Windows、macOS 上的以下能力：

- 接收多个绝对文件/目录路径，能够区分普通路径和虚拟载荷。
- 目标区域命中、拖入/拖出光标反馈和取消回调。
- 是否可安全获得外部拖出目标目录；若不能，禁用拖出而不是猜测路径。
- Windows 长路径/占用文件、macOS sandbox 权限、Linux X11/Wayland 文件管理器差异。
- 插件 native 代码的依赖、许可证、最小权限及崩溃隔离。

在平台验收完成前不得实现或模拟“已支持拖出”；首期只保留外部拖入。

### 2026-07-23 调研结论

- 候选为 `desktop_drop 0.7.1`：官方包页声明 Linux、Windows、macOS 均可接收拖入文件/目录，许可证为 Apache-2.0，且提供 target enter/leave/done 回调，满足首期外部拖入的最小能力。
- 该插件的职责是接收拖入，不提供可信的跨应用拖出目标目录。因此它不能满足本设计的安全拖出前提；首期不实现拖出，也不添加“允许拖出解密副本”设置。
- macOS `DropItem` 可能来自 file promise，文件会被写入应用临时 Drops 目录而非来源普通路径。该载荷必须拒绝，不能把临时副本当作用户选择的导入源。
- 现行代码已将 plugin 载荷收敛为已存在、绝对、普通文件或目录路径；URL、内存字节、file promise、相对路径和 root 内部路径一律拒绝。Windows 分隔符混用也会在控制器边界判断前统一，真实 Windows 资源管理器仍待验收。

## 6. 验收与测试

自动化：

- controller 单测：外部拖入路径/载荷拒绝、Windows 分隔符归一化、root 边界判断、冲突请求映射和取消不创建操作。
- Home widget：拖入目标高亮、放下调用现有导入确认、错误与取消状态、设置关闭时拖出不可用。
- Dart/FFI：拖入调用后与普通导入相同的 unfinished 状态；拖出调用后与普通导出相同的冲突和取消语义。

桌面实测矩阵：

- Linux：X11 与 Wayland，各至少一个文件管理器；多文件、目录、取消和失焦。
- Windows：资源管理器拖入、长路径、目标冲突、占用文件和权限拒绝。
- macOS：Finder、沙箱/安全作用域权限、取消和目标冲突。
- 三平台：默认禁止拖出、开启后明文确认、不会删除加密源、不留下临时明文或 `.safe_disk.transfer.*.lock`。
